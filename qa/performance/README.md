# Ella API: Performance Tests (k6 + Grafana)

Performance tests for the Ella API's **User**, **Product** and **Transaction** endpoints, written in
[k6](https://k6.io). Results stream live to **Grafana** (through InfluxDB). Each run also saves an
HTML report and a JSON summary.

## Project structure

```
qa/performance/
├── src/
│   ├── config/
│   │   ├── enviroment.js      # CONFIG: base URL per environment, think time
│   │   ├── endpoints.js       # ENDPOINTS: /users, /products, /transactions, /health
│   │   ├── threshold.js       # THRESHOLDS per test type (smoke, load, stress, soak)
│   │   └── loadprofiles.js    # smokeOptions(), loadOptions(), stressOptions(), soakOptions()
│   ├── api/                   # one client per API (like page objects)
│   │   ├── client.js          #   HTTP wrapper: base URL, headers, timeout, tags
│   │   ├── userApi.js
│   │   ├── productApi.js
│   │   └── transactionApi.js
│   ├── data/
│   │   ├── payload.js         # userPayload(), productPayload(), transactionPayload()
│   │   └── products.json      # product templates
│   ├── scenarios/             # user journeys (business flows)
│   │   ├── userFlow.js        #   register -> view -> edit (-> list)
│   │   ├── productFlow.js     #   create -> view -> edit -> browse (-> list)
│   │   └── transactionFlow.js #   view product -> buy -> view receipt (-> list)
│   └── utils/
│       ├── checks.js          # status + body checks, business_errors metric
│       ├── data.js            # uniqueId, think time, helpers
│       └── setup.js           # health check, seeding, stock integrity check
├── tests/                     # one file per API x test type
│   ├── user/        smoke.js  load.js  stress.js  soak.js
│   ├── product/     smoke.js  load.js  stress.js  soak.js
│   └── transaction/ smoke.js  load.js  stress.js  soak.js
├── grafana/                   # InfluxDB 1.8 + Grafana 11, auto-provisioned dashboard
├── scripts/run.ps1, run.sh    # runners: Grafana output + HTML/JSON reports
├── reports/                   # generated reports (gitignored)
├── .env.example
└── package.json               # npm shortcuts
```

Every test file is a few lines: it picks a profile from `loadprofiles.js` and runs one flow from
`scenarios/`. To change the load or the SLAs, edit `src/config/`; to change what a user does, edit
`src/scenarios/`.

## Prerequisites

- [k6](https://grafana.com/docs/k6/latest/set-up/install-k6/) v1.x (`choco install k6` / `brew install k6`)
- Docker Desktop (for Grafana + InfluxDB)
- Ella API running, by default at `http://localhost:4000` (`GET /health` must return 200)

> The API has no DELETE endpoints, so every run leaves users, products and transactions behind.
> Run against a disposable or staging database, **never production**.

## Start the Ella API locally (no Docker)

```powershell
npm install          # once: installs a private PostgreSQL
npm run api:start    # PostgreSQL on 5433 + Ella API on 4000; Ctrl+C stops both
npm run api:reset    # same, but wipes the database first
```

Leave it running in its own terminal and run the tests in another one. Data is kept in
`local-env/pgdata/` between runs. By default it starts the API from this repository (`../../`); set `ELLA_API_DIR` to use another checkout.

## Quick start

```bash
# 1. start Grafana + InfluxDB
docker compose -f grafana/docker-compose.yml up -d

# 2. run a test and stream results to Grafana
k6 run --out influxdb=http://localhost:8086/k6 tests/transaction/load.js

# 3. open the dashboard: http://localhost:3000 -> "Ella API - k6 Performance"
```

Or use the runner, which also saves `reports/<testid>.html` and `reports/<testid>.json`:

```powershell
./scripts/run.ps1 -Api user -Type smoke
./scripts/run.ps1 -Api all -Type load -Grafana         # user, product, transaction in turn
./scripts/run.ps1 -Api transaction -Type stress -Grafana -BaseUrl http://localhost:4000
```

```bash
GRAFANA=1 ./scripts/run.sh transaction load
```

npm shortcuts: `npm run smoke`, `npm run user:load`, `npm run validate` (compiles all 12 tests).
Every run (`k6 run tests/...`, `npm run <api>:<type>` or the runner) saves a styled HTML report and the raw
JSON summary as `reports/<api>-<type>-<yyyyMMdd-HHmmss>.html|.json`. The report has cards (requests, failed
requests, breached thresholds, failed checks) and tabs for detailed metrics, per-endpoint timings,
thresholds, run details and checks. It is generated by `handleSummary` in `src/utils/report.js`; run k6
from the project root so `reports/` is found.

## Test types

Defined in [src/config/loadprofiles.js](src/config/loadprofiles.js). Load, stress and soak use an
open model: rates are user journeys *started* per second, so a slow API shows up as rising latency.

| Type | Shape | Duration | Thresholds |
|---|---|---|---|
| `smoke` | 5 VUs | 30 s | p95 < 500 ms, errors < 1%, checks > 99% |
| `load` | 20 → 125/s (hold 5m) → 250/s peak (hold 10m) → 0 | ~22 min | p95 < 1 s, errors < 1% |
| `stress` | 250 → 400 → 600/s, 3 min each | ~18 min | p95 < 2 s, errors < 5%; aborts when errors > 20% |
| `soak` | 125/s held | 2 h (+10 min ramps) | p95 < 1 s, p99 < 2 s, errors < 1% |

Knobs: `-e RATE_SCALE=0.2` scales every rate, `-e SOAK_DURATION=4h`, `-e THINK_TIME_MAX=0`,
`-e BASE_URL=...`, `-e ENV=staging`.

**Sizing note:** with the default 1–5 s think time, one journey takes ~6–10 s, so 250 journeys/s needs
~2,000 concurrent VUs, which is more than `maxVUs: 1000`. k6 reports the shortfall as
`dropped_iterations`. Either raise `maxVUs` or lower the think time for peak tests.

## HTML report

Every run writes `reports/<api>-<type>-<yyyyMMdd-HHmmss>.html` (styled report: summary cards, detailed
metrics, per-endpoint timings, thresholds, run details, checks) and a matching `.json` with the raw
summary. The console shows k6's usual end-of-test summary followed by the two file paths. Both come
from `handleSummary` in `src/utils/report.js`.

```powershell
k6 run tests/user/smoke.js                    # report in reports/
npm run report:user                           # same, plus opens it in the browser
npm run report -- -Api all -Type smoke -NoOpen
```

Run k6 from this folder (the project root) so the `reports/` folder is found. While a test runs through
the runner, k6's live dashboard is also available at http://localhost:5665.

## Grafana dashboard

Every metric carries `testid`, `test_type`, `api` and `name` (endpoint) tags. The dashboard
has **Test run** and **API** dropdowns to filter by them:

- **Overview:** total requests, peak VUs, p95/p99, HTTP error rate, checks passed
- **Load:** VUs vs requests/s, requests/s per API
- **Response time:** p95 per API and per endpoint, percentile bands, and a breakdown of where time
  goes (blocked / connecting / sending / waiting / receiving)
- **Errors:** error rate per endpoint, responses by status code, business errors, dropped iterations
- **Tables:** per-endpoint summary (count, avg, p90, p95, p99, max, error %) and per-check pass rate

How to read it: high **waiting** means the server or database is slow. High **receiving** means
large payloads. **Dropped iterations** means k6 ran out of VUs or the API is saturated.

**No Docker?** Use the HTML report above (live at http://localhost:5665 during a run).
## Endpoints covered

| API | Endpoints |
|---|---|
| Users | `POST /users`, `GET /users/:id`, `PUT /users/:id`, `GET /users` (every 10th iteration) |
| Products | `POST /products`, `GET /products/:id`, `PUT /products/:id`, `GET /products` (every 10th) |
| Transactions | `GET /products/:id`, `POST /transactions`, `GET /transactions/:id`, `GET /transactions` (every 20th) |

The list endpoints are called occasionally, not on every iteration. `GET /products` embeds every
product's full sales history, so its cost grows with each sale. Set `-e PRODUCT_LIST_EVERY=0` to
leave it out, or `=1` to stress it.

## Data integrity check

The transaction tests seed products with 1,000,000 units. After the run it compares units sold with
the stock deducted. On the current build it reports
`DEFECT: purchases INCREASED stock ...`: purchases add stock instead of removing it. Under
concurrency it also detects lost stock updates.
